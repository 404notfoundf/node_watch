# GitHub Release Watch

用 GitHub Actions 监控公开仓库的 Release，比较版本间的代码差异，并调用 AI 审阅矿池和节点可能受到的影响。

- **自动审查**：按币种、版本生成完整报告，支持快速预检和完整 diff 审查。
- **多种输出**：成功审核的版本发布到 Pages、Markdown Artifact 和本轮汇总 Issue。
- **按需通知**：重大风险和适用的上游升级建议触发 `@` 提醒，普通更新不主动提及用户。
- **持续轮询**：支持完成后等待 15 分钟再启动下一轮，失败版本保留待重试。

工作流不会运行上游程序或测试，也不会自动升级矿池节点。AI 静态审阅不能替代人工安全审查。

快速入口：[配置](#配置监控对象) · [Actions 运行](#在-github-actions-中运行) · [通知](#通知设置) · [审核与调度](#审核与调度) · [排查失败](#缓存重试与排查) · [本地运行](#在本地运行)

## 配置监控对象

将 [config/watch.example.yaml](config/watch.example.yaml) 复制为 `config/watch.yaml`，替换仓库、实际运行版本、AI 地址和模型：

```yaml
ai:
  api_url: https://your-compatible-api.example/v1
  model: your-model
  diff_chunk_chars: 120000

coins:
  tari:
    repo: tari-project/tari
    running_version: v6.4.0
    network: mainnet
    include_prereleases: false
```

每个币种配置一个仓库。工作流只读取 `config/watch.yaml`，示例文件不会自动加载。

| 字段 | 用途 |
| --- | --- |
| `repo` | 上游仓库，格式为 `owner/repository`。 |
| `running_version` | 矿池当前实际运行、且已发布的 GitHub Release tag。只审核比它新的版本。 |
| `network` | 实际运行网络，例如 `mainnet`。不填写时，AI 不会假定受影响的是主网。 |
| `include_prereleases` | 设为 `false` 可跳过 GitHub 标记的预发布版及 pre、rc、test、testnet 等发布线。 |

升级矿池节点后，记得同步更新 `running_version`，后续审查会以新版本作为起点。每个币种内部始终按版本顺序比较。

### AI 接口与提示词

使用 OpenAI Chat Completions 兼容接口：

- `api_url` 可以填写以 `/v1` 结尾的根地址，脚本会补上 `/chat/completions`。
- `model` 填服务商支持的模型名称。
- `diff_chunk_chars` 是每段代码差异的字符上限，默认 120,000；按模型上下文窗口调整。
- 所有仓库共用 `AI_API_KEY` Secret，设置步骤见下一节。

全局 `ai.prompt` 只放通用的证据、网络、风险和通知规则，不写某个项目的字段、命令或旧版本的固定结论。

项目专项要求可放在 `coins.<币种>.ai.prompt`，但必须依据当前仓库、目标版本的实际证据判断，不借用其他币种或过去版本的结论。

币种级覆盖的行为：

- `prompt` **替换**全局自定义提示词，不是追加。
- 未覆盖的 `api_url`、`model`、`diff_chunk_chars` 仍继承全局设置。
- 内置证据校验、风险规则和 JSON 输出要求始终保留。
- 覆盖只作用于该币种，完整审核、分块、汇总和快速预检均使用相应设置。

## 在 GitHub Actions 中运行

1. 将本项目推送到 GitHub 默认分支。
2. 填好 `config/watch.yaml`，在 **Settings → Secrets and variables → Actions → Secrets** 添加 `AI_API_KEY`。
3. 在 **Settings → Pages → Build and deployment → Source** 选择 **GitHub Actions**。Pages 报告是公开网页。
4. 在 **Settings → Actions → General → Workflow permissions** 允许工作流 token 写入仓库内容。工作流还使用 `issues: write` 创建 Issue，以及 Pages 部署权限发布网页。
5. 在 **Settings → Environments** 新建 `release-poll-cooldown`，把 **Wait timer** 设为 15 分钟。
6. 在 **Settings → Secrets and variables → Actions → Variables** 添加 `RELEASE_POLL_COOLDOWN_ENABLED`，值设为 `true`。
7. 打开 **Actions → 节点版本审查 → Run workflow**，手动启动一次。

### 轮询间隔与暂停

每轮审查和报告发布完成后，`schedule-next` job 等待 15 分钟，再通过 `workflow_dispatch` 启动下一轮。

这是**完成后再等待 15 分钟**，不是每个整点的固定 15 分钟调度。Environment 等待不占 runner，但实际启动仍受 GitHub runner 排队影响。

- **暂停**：将 `RELEASE_POLL_COOLDOWN_ENABLED` 改为 `false`；当前正在等待的 Environment job 仍需在 Actions 页面手动取消。
- **恢复**：改回 `true`，再手动运行一次“节点版本审查”。

不要重复手动启动。额外运行只会进入同一并发队列，可能替换已排队的运行，并不会让轮询更快。

## 通知设置

### 通知谁

在 **Settings → Secrets and variables → Actions → Variables** 添加或编辑 `NOTIFY_LOGINS`：

```text
alice,bob,charlie
```

填写 GitHub 用户名，用逗号分隔，不带 `@`，不填邮箱。

- 未设置或留空时，默认提及仓库所有者。
- 填写后使用完整名单；自己也要收提醒时，需要把自己的用户名一起填进去。
- 组织账号提及不保证通知全部成员，建议填写具体用户。
- 公开仓库通常不需要把接收人加入协作者；私有仓库需要对方有访问权限。

接收人不要将仓库设为 **Ignore**。只想接收参与和提及通知时，选择 **Participating and @mentions**；Watch 的 Issues 或所有活动选项可能让每条新 Issue 都产生通知。

`@` 提及不保证邮件或手机推送送达，还需检查接收人的个人通知设置。新增接收人不会自动补发已经通知过的版本。

### 什么情况下通知

风险警报和运营升级提醒共用 `NOTIFY_LOGINS`，但不是每轮、每个版本都会主动提及用户。

- **代码风险警报**：有可核实代码证据的 P0/P1 发现。
- **目标网络硬分叉**：明确给出激活高度或升级期限，并要求升级或说明旧节点会分叉离网。
- **重大 Breaking Changes 声明**：章节中有适用于当前目标、可逐字核实的具体影响，标题本身不触发通知。
- **运营升级提醒**：正式版中适用的上游矿池、节点运营者升级建议；单独标为非紧急风险提醒，不抬高 AI 风险等级。

待验证、普通修复或低风险事项本身不会触发代码风险警报，但仍可进入完整报告。

Issue 顶部的**处置概览**列出本轮全部已完成版本的风险、升级建议和**提醒说明**，直接区分“代码风险警报”“上游强烈推荐（运营提醒）”“未触发主动提醒”等原因；**通知触发版本**只列出真正触发提醒的原因，不混入同版本的 P2/P3 发现。下方仍保留各币种的详细结论和代码变化。因此，顶部只有 Alephium 的提醒，不代表 Aleo 或 Bitcoin Knots 未审核；请对照概览及下方详情。没有任何版本达到条件时，仍发布汇总 Issue，但不主动 `@`。

### 升级建议与风险等级

- **必须升级**：P0，或适用于目标网络、明确要求在激活高度／期限前升级的硬分叉声明。代码影响未核实时仍注明需要核对。
- **建议升级（P1）**：尽快核对实际影响并安排处理，不仅凭“兼容性／破坏性已确认”要求所有节点升级。
- **按需升级（P2，无适用上游推荐）**：先核对平台、节点模式及配置；受影响时安排维护窗口，非强制升级，也不单独触发风险警报。
- **可暂缓（P3）**：仅低影响变化或修复，无需立即升级；后续升级前仍应核对监控、配置和客户端调用方式。
- **需人工确认**：重大声明尚未核实；不把待验证当成已确认风险。

正式版的适用上游升级推荐是独立条件：原文明示 `highly/strongly recommended` 或“强烈建议／高度推荐”等时显示**强烈建议升级**，一般推荐显示**建议升级**；即使 P3 也保留推荐和非紧急运营提醒，不抬高代码风险等级。仅出现“重要更新”或与推荐无关的 `highly` 不会强化为“强烈建议”。握手版本号增加但接受范围仍兼容、指标语义或 developer 命令变化、面向未来升级的条件性保护闸门，都不单独证明现网必须升级。上述规则对所有币种共用，无需逐币种编写提示词。

### 上游升级建议

`auto` 会对明确建议运营者升级、或面向矿池和节点的“重要／关键更新”等声明使用完整审查。常见表述包括：

- `highly/strongly recommended`、`recommend upgrading`；
- `encouraged/advised to upgrade`、`should/must upgrade`；
- “强烈建议升级”“矿池重要更新”等。

标题、章节中的网络和对象范围也会纳入判断。其他网络、否定或暂缓建议、仅钱包或开发工具更新、代码围栏示例不会单独触发此规则。

通用运营者建议未说明网络时会保留，但不会据此推断主网共识风险。正式版即使 AI 返回 P3 且没有确认发现，也可按原文强度显示“强烈建议升级 · 需关注”或“建议升级 · 需关注”，并在报告和 Issue 中引用上游原文。例如 Alephium 的矿池强烈升级建议与普通 P2 条件性变化，不再共用同一个处置标签。

- 已有的“必须升级”或“需人工确认”不会被一般升级建议降级。
- 预发布版不会单凭上游推荐触发生产升级提醒，也不建议直接部署生产。
- `fast`、`full` 强制模式仍优先于自动规则。希望每版都审完整 diff 时，设置 `review.mode: full`。

文字规则只识别有明确依据的常见表述，不是任意自然语言的语义判断器。出现漏判的新表述时，应增加对应回归用例。

### 历史版本补审与去重

例如 Alephium `v4.7.2`：高于 `running_version`、有适用上游升级建议、已审核但尚未包含在带 `@` 的汇总 Issue 中时，会重新加入待审队列。

- 补审成功后发布新报告和通知，之后跳过该版本，不会每 15 分钟重复提醒。
- 补审占本轮版本额度；审核或通知发布失败时，后续轮询继续尝试。
- 以机器人 Issue 的版本标记及合法“通知对象”页脚判断已处理、已通知；普通正文 `@` 和非机器人 Issue 不算。
- 不删除历史报告，也不清空全部去重记录。删除历史 Issue 或修改通知页脚，可能再次触发补审。
- 未启用 GitHub Issue 历史读取的本地运行，不会自动补审已处理版本。

## 审核与调度

### 审核模式

`review.mode` 同时作用于 GitHub Actions 和本地 Codex CLI。

| 模式 | 行为 |
| --- | --- |
| `auto` | 默认模式。所有版本按风险信号选择快速预检或完整审查。 |
| `fast` | 强制快速预检，只发送发行说明、变更文件清单及本地扫描发现的可疑片段。 |
| `full` | 强制审查完整 diff；大差异分块审查后汇总。 |

报告会注明实际模式。快速预检不会宣称未发送的代码安全；本地启发式扫描只覆盖已知风险特征，不等同完整安全审查。

`auto` 在以下情况使用完整审查：

- 发行说明涉及共识、硬分叉、认证凭据、密钥清零、交易 gossip 封禁、内存泄漏/OOM、数据库损坏或重置等重大风险。
- 新增命令执行、外部下载、动态加载、疑似密钥外传代码或 CI 权限。
- 改动 Actions、构建/安装/发布脚本，或认证、加密、钱包、链、共识、验证、P2P、RPC、存储、数据库、交易等核心路径，包括删除。
- 有适用的上游运营者升级建议。

### 批量与每轮额度

低风险快速预检默认按 `review.fast_batch_size` 合并最多 3 个版本：

- 每个版本有独立编号，不互相借用证据。
- 缺项、重复、格式异常或输入过长时，退回逐版本预检。
- 高风险版本和完整审查不会批量化。

`review.max_releases_per_run` 默认 `3`，限制单轮进入准备／审核的版本总数，**包含失败尝试**。剩余版本留到下一轮。

### 待审少的先完成

每轮先查询全部币种，再按实际待审数量从少到多安排；数量相同时保持配置顺序。

- 没有待审版本的币种不占名额。
- `include_prereleases: false` 时，测试／预发布版不参与排序，也不占额度；主动开启时正常计入。
- 某个版本失败后，本轮停止该币种的后续版本，其他币种继续使用剩余额度。
- 后续 tag 获取失败时，会先审核已经准备好的较早版本，再停止该币种的后续版本。

### 长期等待保护

连续 3 轮查到待审版本、却未进入准备／审核的币种，下一轮先获得 1 个保护名额，再按剩余队列安排其他额度。多个币种需要保护时，等待最久的先获得机会。

- 获得尝试机会，即使失败，或队列为空后，等待计数清零。
- Release 查询失败时保留旧计数，不凭未知结果增加或清零。
- 等待状态原子写入 `.release-review-cache/scheduler-v1.json`；本地跨轮保留，Actions 沿用 checkpoint 恢复／保存，不需要新数据库或权限。
- 更改仓库、运行版本、网络或预发布版开关后，对应队列按新身份计数。
- 缓存丢失、清理或无效时，等待计数从零开始，但版本去重记录不受影响。

等待按完成调度的轮数统计，不保证固定分钟数。

## 检查范围

只报告实质影响矿工或节点运行的共识、破坏性变更、兼容性、安全、内存、稳定性和数据问题。常规重构、文档、测试、普通依赖更新和低影响修复会略过。

证据与影响判断遵循以下边界：

- **代码发现**：引用精确文件路径和可匹配原文的代码片段，并说明实际调用、行为差异与因果关系。文件名、注释、历史 AI 文本和 PR 元数据本身不能当代码证据。
- **发行说明声明**：独立的 `Breaking Changes` 或 `Breaking Notes` 章节须有具体影响，并引用 `发行说明原文：「…」`；标题单独不证明代码影响，也不触发通知。
- **破坏性／兼容性变更**：证明受支持的升级、迁移、恢复、运行或客户端流程在比较起点可用、目标版本因改动失效。只影响不受支持的旧版只读工具，不作为兼容性问题。
- **目标网络**：只影响其他网络的变化，不冒充当前网络的重大风险。明确硬分叉条件适用于目标网络时，报告和 Issue 将其置于最前；正式版可按上游要求显示“必须升级”，同时标明代码影响是否待核实。
- **实际配置**：对照默认值、官方预设和支持范围。脚本不读取矿池机器上的 `config.toml`；未提供的自定义配置只作条件性说明，不断言当前节点使用了越界值。

“发行说明待核实”只表示发行说明明确声称重大影响，但现有证据仍未确认，不代表已发现问题。每个非“无”的重点标记会在报告和 Issue 中单独列出声明或代码证据。

### 预发布与历史证据

预发布版通过 GitHub 的 `prerelease` 标志或 pre、alpha、beta、rc、dev 等 tag 后缀识别，并按配置决定是否审核；不会建议直接用于生产升级。

正式版可引用同系列预发布报告，但只沿用有明确代码依据、且目标版仍包含相应行为的结论，标为“此前已确认”，不说成本次新增。

- 历史发现缺少当前可验证代码、同系列预发布报告缺失或仍有重大待核实项时，回退到上一个正式版的累计完整 diff。
- 无法证明变化首次进入哪个版本时，明确说明未知。
- AI 建议不实时读取矿池节点状态，也不会自动升级节点或修改 `running_version`。

## 缓存重试与排查

### 分块与证据校验

大 diff 优先按完整文件分段；单个文件超过 `diff_chunk_chars` 才按行拆分。全部差异都参与审查，不省略尾部代码。

每段只发送命中的重大发行说明条目和自定义审查要求，最终汇总仍收到完整发行说明。

分块只有全部通过以下检查，才可缓存或复用：

- 返回裸 JSON，或完整、单一的 Markdown JSON 代码围栏；不从说明文字中截取 JSON，也不自动补全截断响应。
- 包含匹配的 `review_id`、`complete: true` 和结构化 `analysis`。
- 字段、类别、严重度和发现一致性有效。
- 已确认发现的 `path`、`quote` 与该分块代码匹配，不借用其他分块代码；超大文件后续分块仍保留原路径。

分块、完整审核和快速预检共用从校验规则生成的类别状态表。内存问题、安全、稳定性/数据使用 `修复` 或 `风险` 表示代码发现，不使用 `已确认`；无法证实的重大发行说明主张才用 `待验证`。

依据中的分号会在内部字段中转义，展示与通知解析时还原；换行仅在展示时合并，代码证据原文不改写。排版不再导致审核失败，空依据、错误状态、严重度不一致或不匹配的代码证据仍会被拒绝。

完整审核同样接受完整、单一的 JSON 代码围栏，不接受混入说明文字、多对象或截断响应。AI 只输出结构化数据，报告标题、章节和编号由程序生成。

代码证据通过核验后，程序为正文和类别依据补齐遗漏的路径引用；同一类别可以包含多个文件的发现。明确写错路径仍会报错，不会自动改写模型的错误主张。

最终汇总只选择已验证目录中的 `evidence_id`，由程序回填原始路径和引用并再次核验。目录也保留匹配当前代码的历史引用，以及已确认包含在目标 tag 中的关联 PR/commit patch 代码。

**片段匹配只证明引用存在，不证明因果关系成立。** AI 仍需结合目标网络、调用条件和前后行为判断，不会因此自动抬高风险。

### 缓存身份与恢复

- 仅当仓库、比较版本、代码内容、模型、接口地址和提示词均相同，才复用有效分块；读取时重新核验。
- 新协议使用 `chunk-v3` 身份，旧自由文本缓存自动失效；不清空版本、通知记录或 `scheduler-v1` 等待状态。
- 后续分块或最终汇总失败，不丢弃较早的有效分块缓存。
- 修改提示词会改变缓存身份。首次重新审核大 diff 会增加 AI 调用量。

### 重试次数

GitHub 请求、AI 接口请求与审核结果校验重试分开处理：

| 失败类型 | 尝试次数 | 处理方式 |
| --- | --- | --- |
| GitHub API 的网络错误、超时、连接中断，或 HTTP 408、500、502、503、504 | 每次请求最多 4 次 | 首次请求加最多 3 次重试，间隔 5、10、20 秒；分页只重试失败页，日志显示请求路径、错误类型及次数，不输出认证信息。 |
| AI 接口的网络错误、超时、传输 JSON 解析错误、响应截断，或 HTTP 408、429、500、502、503、504 | 每次接口调用最多 4 次 | 首次请求加最多 3 次重试，间隔 5、10、20 秒。 |
| 分块格式、完成标记或代码证据无效 | 最多 2 次审核结果尝试 | 第二次带具体错误、原始分块和标为不可信的上一次答复，保留有证据的发现并重新输出完整对象。 |
| 最终审查 JSON 或证据无效 | 最多 2 次审核结果尝试 | 重试收到校验原因、原始材料、证据目录（多分块）和标为不可信的上一次答复。 |
| 临时 Git 仓库清理失败 | 最多 4 次清理尝试 | 首次清理加最多 3 次重试，间隔 0.2、0.5、1 秒；不重复 Git 拉取或 AI 审核，持续失败只记录清理警告，不作废有效 diff，也不覆盖原始 Git 错误。 |
| 其他 HTTP 错误 | 立即失败 | 不标记为已处理，后续轮询再尝试。 |

GitHub 的 401／403 权限错误、404 和 429 限流不做短间隔重试；应核对权限、仓库路径或限流状态。HTTP 200 返回无效 JSON 也不会当作网络故障重复请求，原始解析错误会保留。Release 查询、Issue 历史及上游 PR／commit 证据查询共用上述 GitHub API 重试；Git 命令与报告发布不在此范围内。

用于比较版本的临时 Git 仓库在 `fetch` 时禁用自动维护，避免后台维护进程与目录清理竞争；不修改主仓库或机器的全局 Git 配置。Git 拉取、diff 或变更路径查询本身失败时，仍不标记为已完成，留待下轮重试。

持续失败的 Release 留待下轮重试。一部分币种失败，不阻止其他成功结果发布。

### 看哪一步日志

先看 **Review new GitHub Releases** 中的具体错误和 `Check pending` 条目。

- 日志会显示请求次数、验证失败、缓存复用及完成验证。
- Git 差异获取失败会立即显示仓库、起止 tag、失败阶段和完整异常堆栈；目录清理失败单独记录为警告，不再盖住原始拉取错误。
- JSON 解析错误包含行、列和响应长度。
- 重点标记错误指出具体类别与字段；状态错误还列出实际值和允许值，不打印依据正文。
- 代码证据错误包含发现／证据序号、文件路径和原因，不打印引用代码或 AI 答复正文。
- **Mark incomplete release checks** 只是本轮存在未完成检查的汇总失败标记，不是原始故障原因。

## 报告与保存期限

每轮成功审核的新版本按币种和版本分段，发布网页、Markdown Artifact 和一条汇总 Issue。没有达到通知条件时，Issue 不主动 `@` 用户。

| 内容 | 保存位置 | 保存期限 |
| --- | --- | --- |
| 在线报告 | 独立 `gh-pages` 分支及 Pages | 180 天；过期目录在下一次发布时从当前网站清理。 |
| Markdown Artifact | GitHub Actions | 最长 90 天。 |
| 版本去重和通知标记 | 机器人汇总 Issue | 不随网页报告过期。 |

Pages 清理不抹去分支的 Git 提交历史。Actions 报告不会提交到默认分支的 `reports/` 目录；Pages 只保存报告及历史审查材料，不作为版本去重状态来源。

每个 Release 的 Markdown 版式由 [.github/scripts/upstream_release_report.md](.github/scripts/upstream_release_report.md) 控制，脚本负责分组和填入数据。

## 在本地运行

需要 Python 3.13、Git 和可访问的公开上游仓库。PowerShell 示例：

```powershell
python -m pip install -r requirements.txt
$env:AI_API_KEY = "your-api-key"
# 也可以改用已安装并登录的 Codex CLI；启用后无需 AI_API_KEY。
# $env:AI_BACKEND = "codex_cli"
python .github/scripts/watch_releases.py
```

本地默认使用 `config/watch.yaml` 的 API。启用 `AI_BACKEND=codex_cli` 后改用本机 Codex CLI。

- 报告写入本地 `reports/`，不创建 Issue，也不上传 Artifact。
- 默认从当前 GitHub 仓库读取机器人 Issue 去重标记；仓库由 `GITHUB_REPOSITORY` 或 Git `origin` remote 确定。
- 公开仓库不需要 GitHub CLI 或 token；私有仓库需要 `GH_TOKEN`。
- 临时设置 `SKIP_GITHUB_ISSUE_HISTORY=1` 可跳过线上历史，此时只按本地报告去重，也不会自动补审已处理的运营升级建议。

GitHub Actions 始终用 workflow token 读取机器人 Issue 历史；本地跳过历史的设置不改变 Actions 去重行为。
